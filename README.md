# Awesome Workflow Templates

A friendly library of <!-- n:total -->365<!-- /n --> ready-to-import automations for Yantra:
email, Telegram, Slack, Google Sheets, Notion, WhatsApp, AI agents, RAG and
more. Pick one, import it, fill in a few setup values and let it run.

Welcome! Whether you want to tame your inbox, answer customers on Telegram or
put an AI agent to work on your team's data, there is a good chance a template
here already does most of the job. Every template is a plain JSON file you can
read before you run it, organised by the service or use case it automates, and
ready for `cdecli workflow create-from-json` or the workflow editor's
**Import** button.

These automations started life in the n8n community, and every one of them
links back to its original (see [Thank you](#thank-you) at the end). We
rebuilt them on Yantra so you can run the same ideas with fewer moving parts.

## Why run them on Yantra

n8n is a wonderful tool, and its community has shared hundreds of brilliant
automations; we learned a lot from them. Rebuilding those same workflows on
Yantra showed us where an AI-first workflow engine can go further:

| | In the n8n original | The same workflow on Yantra |
|---|---|---|
| **AI agents** | A model node, a memory node, an output parser and one node per tool around every agent | One agent node with model routing, memory (a session id), structured output and its own sandbox with a shell and a file system |
| **Files** | Download, unzip, write and read back, each as its own node | The agent works with the files directly in its sandbox |
| **Credentials** | Picked on each node after import | Connectors pick up your credentials from your vault at run time; workflow secrets are filled in at run time and redacted from outputs and logs, so no key is ever in the JSON |
| **Hard-coded values** | Ids, channels and emails the author typed in, spread across nodes | Lifted into named setup values you fill once, in one place |
| **Getting started** | Import, then open and configure each node | Ask the Yantra agent for the template by name and it imports and sets it up with you |

And before you run anything, every template tells you how ready it is (its
[tier](#what-the-tier-column-means)) and exactly what it needs from you
(`template.setup`). No surprises halfway through a run.

The other <!-- n:converted -->360<!-- /n --> templates are converted automatically, and the catalog
reports their step counts honestly (`Steps n8n -> Yantra`). Agent-centred
workflows shrink the same way, because the converter folds every model,
memory, parser and tool helper into the agent node. Branch-heavy workflows can
grow a little: an n8n `If` becomes a condition step plus a Branch node, and a
connector with computed parameters gets a small params step in front of it.
The `template.comparison` block in every file has the numbers for that
template.

## Coming from n8n?

Welcome, you will feel at home. Every template keeps a link to the n8n
workflow it came from (the **Original** column in the catalog below, and
`template.source` inside each file), so you can look up the automation you
already know by name and open the two side by side. Here is how the pieces you
know translate:

| In n8n | On Yantra |
|---|---|
| Manual, Webhook, Chat and Execute Workflow triggers | A **Start** step; inputs arrive with the run (`body` for a webhook, `chatInput` for chat) |
| Schedule Trigger | A **Cron** step, started with `cdecli cron activate <slug>` |
| App triggers (new Gmail message, Telegram update, ...) | A **webhook trigger** step, wherever Yantra has a trigger for that app |
| App nodes (Gmail, Slack, Google Sheets, ...) | **Connector** steps, one connector action each |
| HTTP Request | An **HTTP Request** step, with its keys kept as workflow secrets |
| AI Agent with its model, memory, output parser and tool nodes | One **agent** step with all of that built in, plus its own sandbox |
| Basic LLM Chain and its chat model | An **LLM Chain** step connected to a **Chat Model** |
| Set, Code, Filter, Split Out | **Transform** steps that keep your JavaScript, with `$json`, `$input`, `$('Node')` and `$now` still available |
| If, Switch | A condition step plus a **Branch** step |
| Merge | A **Sync** step that waits for both inputs |
| Loop Over Items | A **Loop** step |
| Credentials picked on each node | Credentials resolved from your vault at run time; none are stored in the JSON |

## Use a template

The easiest way is to ask. Tell the Yantra agent which template you want, by
name, and it imports it, fills in what it can and walks you through the rest
(the `yantra-workflow-templates` skill).

Prefer the command line? Three steps:

```bash
# 1. Pick a template below and download it
curl -LO https://raw.githubusercontent.com/yantra-app/awesome-workflow-templates/main/slack/<slug>.json

# 2. Create the workflow in your organisation
cdecli auth login
cdecli workflow create-from-json -f <slug>.json

# 3. Open it in the editor, or run it
cdecli workflow get <slug>                 # copy "Current version"
cdecli workflow run <slug> --ver <version> --wait
```

You can also drop the same file on **Workflows > Import** in the workflow
editor.

A short checklist before the first run:

- **Project and Environment** on the *Workflow Configs* node:
  `create-from-json` fills them from your session; after an editor import,
  select them there (the ids `cdecli auth status` prints).
- **Setup values** (`template.setupVars`): ids, channels, recipients and base
  URLs the original author had hard-coded. They live as empty keys in the
  Workflow Configs `initialContext` and every step reads them as `{{key}}`, so
  you set each value once, in one place.
- **Workflow secrets** (`template.setupSecrets`): add them in the workflow
  editor's Secrets panel after import. Steps reference them as
  `{"$workflowSecret": "KEY"}` (through an `initialContext` entry such as
  `"openaiApiKey": {"$workflowSecret": "OPENAI_API_KEY"}` and a header like
  `Authorization: Bearer {{openaiApiKey}}`); the engine fills them in at run
  time and redacts them from outputs and logs. No key is ever in the JSON.
- **Run inputs**: pass per-run values with `-d`. Templates converted from a
  webhook read them under `body` (`-d '{"body": {...}}'`), and the same fields
  are also visible at the top level; chat templates read `chatInput`.
- **Connector credentials**: connect one for each connector the template uses
  (`[CONNECTOR_CONNECT]` in Yantra chat, or `cdecli credential create -p
  <connector> ...` locally). Connectors named `yantra-*` are provided by
  Yantra and need none.
- **Schedules** (`template.activation`) start only after
  `cdecli cron activate <slug>`; importing does not start the schedule.

Not sure what a template needs? The `template.setup` list inside the file
names every value, secret, credential and webhook registration, and
`template.tier` tells you whether it runs once they are supplied.

## What the tier column means

We would rather tell you up front than have a run surprise you, so every
template carries a quality verdict computed by `scripts/lib/quality.mjs`
(the same check CI runs): `template.tier`, the `template.blockers` behind it,
and `template.setup`, the list of what you must provide before the first run.
Currently <!-- n:ready -->291<!-- /n --> ready, <!-- n:experimental -->74<!-- /n -->
experimental and <!-- n:verified -->0<!-- /n --> verified.

| Tier | Meaning |
|---|---|
| Verified | A person imported and ran it end to end (listed in `data/verified.json`). |
| Ready | Runs once its declared setup is supplied: setup values (`template.setupVars`), workflow secrets (`template.setupSecrets`) and connector credentials. No step approximates the original. |
| Experimental | A step does not run as shipped: a hard approximation (for example a multipart upload the JSON-only HTTP step cannot send), a per-item loop flattened into one pass, a connector action waiting to be published, or a value the converter could not declare as setup (a file the original passed as binary). Review before relying on it. |

Blocker codes: `hard-approximation`, `loop-flattened`, `action-pending-publish`
(a connector patch that is not published yet; the template promotes on the
next catalog refresh after it ships), `unimplemented-action`, `unmapped-node`,
`signature-verification`, and the value codes `missing-required-param`,
`http-auth-missing`, `placeholder`, `upstream-literal-id`, `personal-email`,
`secret-as-input`, which only appear when a value could not be declared as a
setup value or secret (all experimental); `webhook-registration` and
`trigger-replaced` are informational. There is no separate "needs setup" tier:
author ids, personal emails, placeholders and missing connector ids are
lifted into setup values, and every credential into a workflow secret. The
older `status` field is kept for existing consumers: `ready` when the tier is
ready or verified, otherwise `needs-setup`.

Each file's `template.conversion` block lists exactly what was approximated,
folded or stubbed (`conversion.hints` has the converter's notes), and
`template.notes` carries the original author's notes.

## How the conversion works

For the curious: `scripts/convert-n8n.mjs` reads the upstream n8n exports and
produces the Yantra graphs deterministically (`npm run sync`). The main rules:

- Integration nodes become `NodeCdeConnector` steps running one cdecli
  connector action. Parameter names are mapped explicitly for the common
  services in `scripts/lib/n8n-mapping.mjs`; the long tail is matched by
  name and flagged.
- LLM chains use `NodeLlmChain` for text or structured output, connected to
  `NodeChatModel` for the provider, model and credential. Agents use
  `NodeCdecliAgent`. Model, memory, parser and tool helpers become AI
  configuration or agent settings.
- `Set`, `Code`, `If`, `Switch`, `Filter` and the item-list nodes become
  `NodeTransform` steps whose JavaScript keeps the original expressions, with
  shims for `$json`, `$input`, `$('Node')`, `$now` and friends.
- Explicit item loops use `NodeLoop`: each body returns through `NEXT`, and
  final steps receive the collected results after `onDone`. Batch boundaries,
  nested loops and branch return paths are preserved.
- Automatic retry and polling cycles use `NodeRepeatUntil`, retaining retry
  state, interval waits, and selected exit branches. Attempt limits are explicit;
  exhaustion fails the run. Human-response cycles, searches with early exits,
  and execution-history cycles still carry `loop-flattened` until their
  dependencies can be preserved.
- Schedules become `NodeCron`; provider events with a Yantra trigger slug
  become `NodeCdeWebhookTrigger`; everything else starts from `NodeStart`
  with the expected run inputs seeded in Workflow Configs.
- Every template gets one `NodeWorkflowConfigs` node and an `End` node.
- An operation n8n left out of the export is that node's own default for
  the resource (Gmail labels list, Airtable bases list), never another
  resource's default.
- Nothing is faked to make a step pass: crypto the Transform runtime cannot
  compute fails closed, SQL values are escaped or passed as row fields, and
  credentials found in an original are removed.
- Workflows published twice upstream (byte-identical) are converted once;
  `templates.json` `aliases` maps the old path to the kept one.

`data/connector-actions.json` is the ground truth for connector actions and
trigger slugs, built from the pinned published connector registry
(`npm run catalog`). `npm run validate` checks every template against it,
against `data/template.schema.json`, against the node socket catalog in
`scripts/lib/yantra-nodes.mjs`, and against the quality gate.

This collection would not exist without the n8n community. We took
[Awesome n8n Templates](https://github.com/enescingoz/awesome-n8n-templates)
by [Enes Cingoz](https://github.com/enescingoz) as our reference and starting
point, together with the work of the community authors who first designed and
shared each workflow there. Our thanks also go to the [n8n](https://n8n.io)
team for building the tool that made these automations so easy to create and
share in the first place.

What we changed: every workflow was converted from its n8n export into the
Yantra workflow format (a few were rebuilt by hand), credentials were removed,
and hard-coded values were lifted into setup values. Each file names its
original and the upstream commit it came from under `template.source`, and the
catalog's **Original** column links straight to it, so you can always compare
the two side by side.
